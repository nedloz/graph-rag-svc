# graph-rag-svc

Сервис поиска контекста и генерации ответа на вопрос пользователя. Сейчас работает пайплайн
ноутбука соседней команды: быстрые ответы, гибридный поиск (pgvector + BM25), LLM-реранк,
агрегация по документам и ответ LLM через `llm-proxy` (§4.1). GraphRAG отключён.
Заменил собой связку `rag-svc` (ретривал) + `llm-svc` (генерация), обе удалены из проекта.

> **Этот документ — общий для двух команд.** Сервис используется двумя разными проектами:
> нашим (веб-чат на микросервисах с `chat-svc`) и соседним (Telegram-бот без микросервисной
> архитектуры). Разделы 1–9 описывают сервис как он есть сейчас. Разделы 10–12 — различия
> между проектами, предлагаемый компромисс и открытые вопросы, по которым нужно договориться.

---

> **Пайплайн ноутбука вместо прежнего ретривала, GraphRAG отключён** (спецификация
> `main/docs/superpowers/specs/2026-10-27-notebook-pipeline-design.md`). Устройство — §4.1.
>

> - `route_used` — теперь `quick_answer` (готовый ответ из базы быстрых ответов, LLM не вызывалась,
>   `sources` пуст) или `hybrid` (поиск, реранк, ответ LLM). Значений `graph`, `vector`,
>   `graph->vector` больше нет — проверьте, не ветвится ли на них бот.
> - `sources[].score` и `scores_json` — оценка LLM-реранка (0–1), а не косинусная близость.
>   Соседние чанки, добавленные к попаданиям, и все чанки при неразобранном ответе реранка
>   получают 0.

>   нём не учтены. У быстрого ответа поля `usage` равны `null`.
> - Длинный вопрос и история обрезаются (4000 / 4000 на реплику / 24000 всего), а не отклоняются.
>

## 1. Назначение и границы сервиса

### 1.1 Что сервис делает

1. **Принимает вопрос пользователя** и возвращает на него сгенерированный ответ, опирающийся
   на верифицированную базу знаний ВШЭ (документы в схеме `library`).
2. **Отдаёт готовый ответ без LLM**, если вопрос совпал с одним из быстрых ответов
   (`library.quick_answers`, импорт Excel через `db-svc`).
3. **Ищет контекст пайплайном ноутбука** (§4.1): переписывание вопроса с историей, гибридный
   поиск (pgvector + BM25), LLM-реранк, выбор 1–2 документов с соседними чанками, ссылки
   из `library.links`.
4. **Генерирует ответ** через LLM (только через `llm-proxy`) с guardrails в системном промпте и
   проверкой выбранного контекста на признаки prompt injection.
5. ~~Строит и пересобирает граф, владеет онтологией~~ — **отключено** вместе с GraphRAG; код
   (`cli/build_graph.py`, `app/ontology`) остаётся с пометкой `DISABLED`.
7. **Отдаёт метаданные ретривала** (какие чанки/документы использованы, скоры, тайминги) —
   чтобы вызывающая сторона могла их сохранить и показать источники.

### 1.2 Что сервис НЕ делает (границы)

Это важнее списка возможностей: сюда не нужно приносить задачи из этого списка.

| Не делает | Кто делает |
| :-- | :-- |
| Аутентификацию пользователей, профили, роли | `auth-svc` |
| Хранение истории диалога, сессий, сообщений | вызывающая сторона (`chat-svc` / бот) |
| Хранение документов и файлов | `library-svc` + MinIO |
| Скачивание и обновление документов | краулер (ещё не написан) |
| Парсинг документов и нарезку на чанки; эмбеддинги быстрых ответов и ссылок | `ingest-worker` |
| Вычисление эмбеддингов | `embedding-svc` |
| Выбор провайдера и модели LLM, ключ роутера | `llm-proxy` |
| Доставку ответа конечному пользователю | вызывающая сторона |
| Модерацию, рейтинги, фидбек | вызывающая сторона |

Сервис **не хранит состояние диалога между запросами**: каждый вызов `/generate`
самодостаточен. Всё, что нужно для ответа, должно прийти в запросе.

## 3. Архитектурные решения (зафиксированы)

Эти решения приняты и не пересматриваются без явного обсуждения обеих команд. Пункты 2–5
относятся к GraphRAG и сейчас не действуют: граф отключён (см. начало документа).

1. **`rag-svc` и `llm-svc` устранены, их заменяет один сервис** — и ретривал, и генерация.
   Причина: `llm-svc` был однофайловым сервисом без библиотечной границы, держать его
   отдельным сетевым хопом позади ретривала означало воспроизвести ту же проблему латентности
   и сложности из двух сервисов, которую миграция и должна была убрать.
2. **Отдельного чанкования для graph-RAG нет.** Вход для извлечения триплетов — те же
   `library.chunks`, что и для векторного индекса (их создаёт `ingest-worker`).
3. **Построение графа отвязано от живого ингеста** — ручной, но полностью повторяемый batch-
   инструмент, способный пересобрать граф по текущим чанкам.
   Отдельная схема «shadow-run + swap после валидации» не понадобилась: `graph.entities` и
   `graph.relations` пишутся через upsert по естественным ключам (`entity_type+canonical_name`,
   `subject+object+relation`), поэтому повторный прогон аддитивен и идемпотентен сам по себе.
   Обратная сторона: устаревшие сущности удалённых документов не вычищаются.
4. **Граф хранится в Postgres** (схема `graph`), не в Neo4j и не в памяти. Обоснование: весь
   стек проекта уже на Postgres, у команды нет опыта с graph-DB. Компромисс: обход через
   рекурсивные CTE менее выразителен, чем Cypher, но не требует новой инфраструктуры.
5. **Извлечение сущностей — один общий модуль** (`app/ontology/extractor.py`), используемый
   и оффлайн (построение графа), и онлайн (разбор вопроса). Двух реализаций быть не должно.

## 4. Как сервис устроен внутри

### 4.1 Онлайн-пайплайн (обработка вопроса) — пайплайн ноутбука

Перенесён из ноутбука соседней команды (`MIEM_Last_Stable_Pipeline.ipynb`), код — `app/pipeline/`;
порядок шагов и константы — как в ноутбуке (номера ячеек указаны в docstring модулей).

```
POST /generate ──► JobQueue (LLM_HTTP_CONCURRENCY воркеров; общая для sync и ws_bridge)
                    │
                    ├─ [0] generation_started (ws_bridge); вопрос и история обрезаются (limits.py)
                    │
                    ├─ [1] быстрый ответ (quick_answers.py): нормализованный вопрос → эмбеддинг
                    │      kind=query → dense по library.quick_answer_variants + BM25 по их текстам,
                    │      RRF 1.5/1.0; пороги RRF ≥ 0.04 и косинус ≥ 0.83 → готовый ответ из базы,
                    │      LLM не вызывается, route_used = "quick_answer"
                    │
                    ├─ [2] переписывание вопроса с историей (rewrite.py, LLM; только если история есть)
                    │
                    ├─ [3] кандидаты (hybrid.py, index.py): pgvector top-60 по library.chunk_embeddings
                    │      + BM25 top-60 по индексу в памяти → RRF 1.0/0.9 → top-40
                    │
                    ├─ [4] LLM-реранк одним вызовом (rerank.py): первые 28, текст до 1100 символов,
                    │      top-18; неразобранный ответ модели → порядок RRF с оценкой 0
                    │
                    ├─ [5] агрегация по документам (context.py): веса 1/0.55/0.30/0.15, 1–2 документа,
                    │      до 9 чанков с соседями ±1, контекст до 18000 символов
                    │
                    ├─ [6] ссылки (links.py): top-3 из library.links, косинус > 0.75 (http:// тоже)
                    │
                    ├─ [7] ответ LLM потоком (prompts.py: FINAL_SYSTEM с guardrails и одним правилом
                    │      языка; температура 0.3, до 1100 токенов) → stream_chunk / BufferSink
                    │
                    └─ [8] message_completed или sync-ответ (route_used = "hybrid");
                           аналитика rag.retrieval_runs
```

**LLM — только через `llm-proxy`.** Все три вызова (переписывание, реранк, ответ) идут клиентом
`openai` на `LLM_BASE_URL` (`http://llm-proxy:8080/v1`, с mTLS-оверлеем `https://llm-proxy:8443/v1`)
с `model: "default"` и ключом-заглушкой. Провайдера, модель и ключ выбирает прокси по своему
`config.json` (`main/infra/llm-proxy/README.md`); кода провайдеров в сервисе нет
(`app/generation/llm_client.py`). Повторы SDK отключены (`max_retries=0`): зависший upstream не
держит воркер 3 × таймаут, а 5xx роутера не превращается в три платных запроса.

**Ошибки.** Сбой любого шага до ответа (embedding-svc, вызов LLM в переписывании или реранке,
база) — ошибка всего задания: `502` в `sync`, `message_error` в `ws_bridge`. Ответ без контекста
не отдаётся.

**Индекс базы знаний** (`app/pipeline/index.py`, `runtime.py`). BM25 по чанкам строится при
старте из `library.chunks` проиндексированных документов. Текст для BM25 — «Название документа /
Категория / Раздел / Текст», тот же, что `ingest-worker` отправляет на эмбеддинг. Раз в
`INDEX_REFRESH_INTERVAL_SEC` (60 с) сервис сверяет сигнатуру (число чанков и последний
`indexed_at`) и при изменении перестраивает индекс в фоне. Не загрузился индекс при старте —
сервис не стартует; пустой индекс — только предупреждение.

Ограничения индекса и поиска:
- Переименование документа или смена категории сигнатуру не меняют: BM25 и реранк видят старые
  название и категорию, пока документ не переиндексируют.
- BM25 отдаёт top-60 вместе с нулевыми оценками (как в ноутбуке), поэтому в RRF попадают и
  чанки без единого совпадающего слова.
- Чанки, проиндексированные после построения снимка, до следующего обновления в выдачу не попадают.
- HNSW отдаёт не больше `hnsw.ef_search` строк, а фильтры по модели и статусу документа
  применяются после обхода индекса. Поэтому на время запроса ставится
  `hnsw.ef_search = max(200, k)`, а на pgvector ≥ 0.8 ещё `hnsw.iterative_scan = strict_order`.
- BM25 быстрых ответов строится на каждый запрос, `get_scores` BM25 чанков считается на цикле
  событий: на сотнях вариантов и тысячах чанков это миллисекунды, при росте базы — кандидат на кэш.

**Пределы входа** (`app/pipeline/limits.py`): вопрос обрезается до `MAX_QUESTION_CHARS` (4000),
каждая реплика истории — до `MAX_HISTORY_MESSAGE_CHARS` (4000), затем самые старые реплики
отбрасываются, пока история не уложится в `MAX_HISTORY_CHARS` (24000). Длинный ввод обрезается, а
не отклоняется: `422` сломал бы контракт бота. В аналитику пишется исходный вопрос.

**Prompt injection.** Выбранные чанки проверяются эвристиками `injection_defense.py`, признаки
пишутся в лог. При `FAIL_CLOSED_ON_INJECTION=true` задание завершается ошибкой до генерации
(`502` / `message_error`). **Это изменение поведения:** раньше при `true` ответ генерировался без
контекста. По умолчанию `false`; включать — только с согласия владельца проекта.

В режиме `ws_bridge` ответ уходит не в HTTP-ответ, а в **исходящее WebSocket-соединение, которое
сервис открывает сам** к `chat-svc` (`CHAT_WS_URL`), см. §5.2 и §10.3.

Ретривал происходит **внутри** сервиса: вызывающая сторона не присылает `rag.chunks`
(в отличие от старого контракта `llm-svc`, где их заранее клал `rag-svc`).

## 5. Внешний контракт (API)

Все эндпоинты требуют межсервисной аутентификации (§5.5).

### 5.1 `POST /generate`

Обязательным является только `question`. Всё остальное опционально, поэтому один контракт
обслуживает и наш веб-чат, и Telegram-бот соседней команды.

```jsonc
{
  "question": "Как получить справку об обучении?",   // единственное обязательное поле

  "response_mode": "sync",              // "sync" (по умолчанию) | "ws_bridge"
  "delivery": {                         // обязателен ТОЛЬКО при response_mode="ws_bridge"
    "assistant_message_id": "c9f0f895-...",  // UUID строки в chat.messages
    "message_id": "6512bd43-..."             // UUID сообщения пользователя
  },

  "request_id": "e3b0c442-...",         // опц., генерируется сервисом, если не передан
  "session_id": "8f14e45f-...",         // опц.; обязателен при response_mode="ws_bridge"
  "user_id": "tg:123456",               // опц., произвольная строка — не обязана быть UUID

  "profile": { "faculty": "МИЭМ", "year": 1 },      // опц., принимается, но не используется
  "history": [                                       // опц., сообщений сколько угодно
    { "role": "user", "content": "..." },
    { "role": "assistant", "content": "..." }
  ]
}
```

**Режим `sync`** — ответ возвращается прямо в HTTP-ответе:

```jsonc
200 OK
{
  "request_id": "...",
  "answer": "Справку об обучении можно получить ...",
  "route_used": "hybrid",                 // quick_answer | hybrid (graph/vector больше нет)
  "sources": [                            // у quick_answer — []
    { "doc_id": "...", "title": "Положение об организации ...",
      "chunk_ids": ["...", "..."], "score": 0.9 }   // score — оценка LLM-реранка
  ],
  "retrieval": { "retrieval_ms": 431, "chunks_used": 6,
                 "retrieved_chunk_ids": [...], "retrieved_doc_ids": [...] },
  "usage": { "prompt_tokens": 1820, "completion_tokens": 240, "total_tokens": 2060 }
}
```

```jsonc
502 Bad Gateway   // ошибка ретривала или генерации; ответ без контекста не отдаётся
504 Gateway Timeout   // не уложились в SYNC_RESPONSE_TIMEOUT_SEC
```

**Режим `ws_bridge`** — ответ уходит потоком в chat-svc, здесь только подтверждение приёма:

```jsonc
200 OK
{ "status": "accepted", "request_id": "...", "assistant_message_id": "...", "queue_size": 3 }
```

Общее для обоих режимов:

```jsonc
429 Too Many Requests   // очередь заполнена (MAX_QUEUE_SIZE)
{ "detail": "queue is full" }
```

Оба режима проходят через одну очередь, поэтому ограничение параллелизма общее.

**История диалога.** Количество сообщений не ограничено; длинный ввод обрезается (§4.1, «Пределы
входа»). Последние 10 реплик идут в переписывание вопроса (самостоятельная формулировка для
поиска), последние 6 — в промпт ответа блоком «История текущего диалога». Роль `system` не
принимается: содержимое истории пишет пользователь, и системная реплика означала бы возможность
переопределить правила безопасности.

**Профиль** принимается для совместимости, но в промпт не попадает: промпт ноутбука его не
использует.

**`usage`** — токены только финального ответа (вызовы реранка и переписывания не учитываются);
у быстрого ответа поля равны `null`.

**Поле `consumer`** заполняется сервером из проверенного имени вызывающего (CN сертификата), а не
телом запроса, и используется в аналитике (§6.2), чтобы различать трафик двух команд.

### 5.2 Доставка ответа в режиме `ws_bridge`: события WS-моста

Сервис сам подключается клиентом к `CHAT_WS_URL` (по умолчанию
`ws://chat-svc:8000/ws/internal/llm`), переподключается каждые 2 секунды при разрыве,
и шлёт туда события по мере генерации.

| Событие | Когда | Поля |
| :-- | :-- | :-- |
| `generation_started` | сразу при взятии джоба из очереди, **до ретривала** | `request_id`, `session_id`, `assistant_message_id`, `message_id` |
| `stream_chunk` | на каждый токен/фрагмент | `request_id`, `session_id`, `assistant_message_id`, `delta` |
| `message_completed` | после завершения генерации | + `query_embedding_model`, `filters_json`, `retrieved_chunk_ids`, `retrieved_doc_ids`, `sources`, `scores_json`, `retrieval_ms`, `route_used`, `prompt_tokens`, `completion_tokens`, `total_tokens` |
| `message_cancelled` | генерацию остановил пользователь (§5.3) | те же поля, что у `message_completed` |
| `message_error` | при ошибке ретривала, LLM или необработанном исключении | `request_id`, `session_id`, `assistant_message_id`, `message` |

Гарантии: `generation_started` всегда первым; далее либо N × `stream_chunk` и один из
`message_completed` / `message_cancelled` / `message_error` (после двух последних генерация
прекращается). Полный текст ответа в этом режиме **нигде не передаётся целиком** —
потребитель обязан склеить его из `delta`. В режиме `sync` текст возвращается целиком (§5.1).

Поле `sources` — документы-источники в человекочитаемом виде, собранные последним этапом
перед отправкой:

```jsonc
"sources": [
  { "doc_id": "8f14e45f-...", "title": "Положение об организации ...",
    "chunk_ids": ["c9f0f895-...", "45c48cce-..."], "score": 0.82 }
]
```

UUID при этом остаются обязательными и никуда не деваются (`retrieved_doc_ids`,
`retrieved_chunk_ids`, `chunk_ids` внутри `sources`) — по ним потребитель строит ссылки на
документы; названия нужны только для отображения. Как именно превращать `doc_id` в ссылку,
решает следующий этап обработки, а не этот сервис.

### 5.3 `POST /cancel`

Останавливает генерацию по `request_id` — и уже идущую, и ещё стоящую в очереди.

```jsonc
// запрос
{ "request_id": "e3b0c442-..." }
// ответ
{ "status": "cancelling", "request_id": "e3b0c442-..." }
// 404 — задание не найдено (скорее всего, уже завершилось)
```

Отмена кооперативная: событие проверяется между фрагментами генерации, поэтому задание
завершается штатно и уже накопленный текст сохраняется, а не теряется посреди записи. В режиме
`ws_bridge` результатом будет событие `message_cancelled`, в `sync` — обычный ответ с
дополнительным полем `"status": "cancelled"` и частичным текстом.

### 5.4 `/internal/graph/*` — курирование графа (отключено)

Маршруты не подключены (GraphRAG отключён), запросы получают `404`; описание ниже — история.
Отдельная группа эндпоинтов для ручной правки графа: поиск и карточка сущности, склейка
дубликатов, смена типа, алиасы, связи, «сироты», стоп-лист и запуск пересборки. Полное
описание и правила — [§13.3](#133-внутреннее-api-курирования-графа-проблема-9).

### 5.5 `GET /ping`, `GET /healthz`

`/healthz` → `{"status":"ok"}`. `/ping` дополнительно отдаёт диагностику: `service`,
`llm_base_url` (адрес `llm-proxy`), **`chat_bridge_connected`** (подключён ли мост), `queue_size`,
`workers` (число воркеров), `active_jobs`.

### 5.6 Межсервисная аутентификация

Статических токенов нет. Вызывающего подтверждает клиентский сертификат (mTLS), а прокси-сайдкар
получателя передаёт имя из сертификата приложению в заголовке `X-Caller-Identity`
(`main/infra/mtls`). Заголовку верят только от loopback; запрос с другого адреса или без
заголовка → `403`. `INTERNAL_AUTH_MODE=insecure` отключает проверку и нужен только для
отладки без PKI; в этом режиме `consumer` берётся из `X-Service-Name` и ничем не подтверждён.

**Для соседней команды (Telegram-бот):** по умолчанию режим `mtls`, то есть запросы без прокси
с сертификатом получат `403`. Либо поставьте перед сервисом такой же прокси, либо задайте
`INTERNAL_AUTH_MODE=insecure` в своём развёртывании.

## 6. Что сервис ожидает от окружения

Это и есть «правила работы» со стороны остальных сервисов.

### 6.1 От вызывающей стороны (`chat-svc` или бот)

**Общее для обоих режимов:**

1. **Прислать `question`** — единственное обязательное поле (§5.1).
2. **Обрабатывать `429`** — очередь переполнена, запрос не принят.
3. **Не присылать `rag`** — ретривал выполняется внутри сервиса.
4. **Быть готовым к отказу вместо ответа**: если ретривал не дал контекста, сервис вернёт
   ошибку, а не ответ без источников. Это осознанное решение — по официальным вопросам
   ответ без опоры на документы хуже честной ошибки.
5. **Передавать историю диалога**, если она есть. Без неё уточняющие и местоименные вопросы
   («а что насчёт пересдачи по ней же?») не переписываются в самостоятельные, и поиск идёт по
   обрывку вопроса.

**Дополнительно для `response_mode="ws_bridge"`:**

6. **Прислать `session_id` и объект `delivery`** — без них запрос отклоняется (`422`).
7. **Держать открытым WS-эндпоинт `/ws/internal/llm`** и принимать по нему пять типов
   событий (§5.2). Если эндпоинта нет — ответ доставить некуда.
8. **Самостоятельно склеивать текст** из `delta` и сохранять его.
9. **Считать `accepted` только подтверждением приёма**, а не признаком успеха.
10. **Ожидать, что `retrieved_chunk_ids`/`retrieved_doc_ids` могут быть `null`** — например,
    если генерация была отменена до завершения ретривала.

### 6.2 От Postgres

Пайплайн читает из `library` (роль `graph_user`, `library_ro`): `documents` (`id`, `title`,
`category`, `ingest_status`, `indexed_at`), `chunks` (`id`, `document_id`, `chunk_index`,
`section_path`, `text`), `chunk_embeddings` (`chunk_id`, `embedding`, `embedding_model`),
`quick_answers` (`question`, `answer`, `is_active`), `quick_answer_variants` (`text`, `embedding`,
`embedding_model`), `links` (`description`, `url`, `embedding`, `embedding_model`, `is_active`).
Сравниваются только векторы с `embedding_model`, равным модели вопроса. Векторы `VECTOR(768)`;
таблицы и переход на 768 — миграция `011_notebook_pipeline.sql`, права воркера — `012`.

Схема `graph` (DISABLED; сервис владеет, полный CRUD) — история:

```
graph.entities              id, entity_type, canonical_name, name_embedding VECTOR(1024),
                            embedding_model, attributes_json, created_at, updated_at
                            UNIQUE(entity_type, canonical_name)
graph.entity_aliases        id, entity_id→entities, alias, alias_normalized, source
                            UNIQUE(entity_id, alias_normalized)
graph.relations             id, subject_entity_id→entities, object_entity_id→entities,
                            relation, confidence, extraction_run_id→extraction_runs
                            UNIQUE(subject_entity_id, object_entity_id, relation)
graph.entity_source_chunks  id, entity_id→entities, relation_id→relations,
                            chunk_id→library.chunks, CHECK(entity_id OR relation_id)
graph.extraction_runs       id, run_type, extraction_model, ontology_version, document_ids[],
                            status, stats_json, started_at, finished_at
graph.curation_blocklist    id, name_normalized (UNIQUE), reason — имена, которые
                            построение графа не должно создавать заново (§13.3)
```

Индексы: hnsw (или ivfflat при отсутствии hnsw и ≥10000 строк) по `entities.name_embedding`,
btree по `entity_aliases.alias_normalized`, `relations.subject/object`,
`entity_source_chunks.chunk_id`.

**Требование к размерности:** `library.chunk_embeddings.embedding` — `VECTOR(EMBEDDING_DIM)`
(768 под `intfloat/multilingual-e5-base`). Значение объявляется один раз в корневом `.env` и
сверяется при запуске с моделью и с фактическим типом колонки — при расхождении сервис не
стартует (§13.1). `graph.entities.name_embedding` осталась `VECTOR(1024)` и не проверяется.

Плюс схема `rag` — нейтральная аналитика ретривала, общая для обоих проектов:

```
rag.retrieval_runs          id, request_id, consumer, session_id, user_id, question,
                            route_used, query_embedding_model, retrieved_chunk_ids[],
                            retrieved_doc_ids[], scores_json, retrieval_ms,
                            prompt_tokens, completion_tokens, total_tokens,
                            status, error, created_at
```

Пишет её сам сервис при каждом завершении запроса (успех, ошибка, отмена). Колонка
`consumer` берётся из проверенного заголовка `X-Service-Name` и разделяет трафик двух
команд. `chat.rag_runs` при этом сохраняется — там есть связь с `message_id`, которой у
бота нет. Запись аналитики никогда не ломает ответ пользователю: ошибка только логируется.

DDL: `main/infra/db/init/init.sql` (новые окружения) и миграции `002_graph_schema.sql`,
`003_graph_curation.sql`, `004_rag_analytics.sql`, `011_notebook_pipeline.sql`,
`012_notebook_grants.sql` (ручное применение к существующим БД).

### 6.3 От `embedding-svc`

- `POST /embed` `{texts:[...], normalize:true, kind:"query"}` → `{model, dimension, embeddings:[[...]]}`.
  Вопросы (и для быстрых ответов, и для поиска чанков и ссылок) идут с `kind="query"`; префикс
  `query: ` модели e5 ставит сам `embedding-svc`.
- `GET /ping` → `{model, dimension, ...}` — используется при запуске для сверки размерности.
- Должен возвращать **ровно `EMBEDDING_DIM` измерений** (768 для `intfloat/multilingual-e5-base`).
  Расхождение с этим значением или с типом колонок в БД останавливает запуск сервиса
  (`app/core/startup_checks.py`), а не всплывает ошибкой на первом же запросе.
- Является **единственным источником эмбеддингов** в системе: `ingest-worker` тоже считает
  векторы через него, поэтому чанки и запросы гарантированно в одном пространстве.
- Пускает `graph-rag-svc` и `ingest-worker` по их клиентским сертификатам (`main/infra/mtls/embedding-svc.conf`).
- Таймаут вызова со стороны graph-rag-svc — 60 секунд.

### 6.4 От `ingest-worker` и краулера

- `library.chunks` заполнены, документы имеют `ingest_status='indexed'` и `indexed_at` — иначе
  индекс пуст и поиск ничего не находит. Новый или переиндексированный документ попадает в
  индекс при следующей проверке сигнатуры (до 60 с).
- `chunk_index` монотонен внутри документа — по нему берутся соседние чанки `±1`.
- Векторы чанков, вариантов быстрых ответов и ссылок считает `ingest-worker` с `kind="passage"`
  той же моделью; строки без вектора в поиске не участвуют.

### 6.5 От `llm-proxy`

- `POST /v1/chat/completions` (OpenAI-совместимый API) на `LLM_BASE_URL`, обычный и потоковый (SSE)
  ответ. Сервис шлёт `model: "default"` и ключ-заглушку; прокси подставляет модель режима и свой
  ключ (`ROUTER_KEY` — только в окружении прокси) и выбирает upstream: внешний роутер или Ollama.
- Под mTLS прокси сам слушает 8443 и пускает только CN `graph-rag-svc` и только
  `POST /v1/chat/completions` (`main/infra/mtls/llm-proxy.conf`).
- Нет корректного `config.json` или ключа в режиме router → прокси отвечает `503`, недоступный
  upstream → `502`; для сервиса это ошибка задания (`502` в `sync`, `message_error`).
- Ollama (профиль compose `llm`) — только резерв для режима `ollama` прокси. Сервис к Ollama
  не обращается, переменных `LLM_PROVIDER`, `OLLAMA_*`, `OPENAI_*` и сборки `WITH_LOCAL_LLM` больше нет.

## 8. Запуск graph-builder (отключено)

> `DISABLED`: GraphRAG отключён, инструмент не поддерживается; раздел сохранён как история.

Инструмент поставляется в том же образе, что и API, и запускается разово:

```bash
# полная (пере)сборка по всем документам с ingest_status='indexed'
docker compose run --rm graph-rag-svc python -m cli.build_graph --full-rebuild

# только конкретные документы
docker compose run --rm graph-rag-svc python -m cli.build_graph --document-id <uuid> --document-id <uuid>

# smoke-тест хранения/резолюции на старых триплетах из ноутбука (НЕ продакшн-граф)
docker compose run --rm graph-rag-svc python -m cli.bootstrap_from_jsonl research/chunks_part_1.jsonl --limit 500
```

Прогон идемпотентен: повторный запуск переутверждает существующие факты и добавляет новые.
Каждый прогон пишет строку в `graph.extraction_runs` со статистикой.

**Перед первым запуском на реальных данных** проверьте, что чанки вообще есть:

```sql
SELECT ingest_status, count(*) FROM library.documents GROUP BY ingest_status;
SELECT count(*) FROM library.chunks;
```

### 9.1 Описание проблем

**Критичные для эксплуатации:**

1. ~~**Нет таймаутов на вызовы LLM.**~~ **Исправлено.** Оба клиента создавались с
   `timeout=None`, и зависший провайдер вешал воркер навсегда, а при `LLM_HTTP_CONCURRENCY=1`
   — всю очередь. Теперь действует `LLM_REQUEST_TIMEOUT_SEC`; для стриминга это пауза между
   фрагментами, поэтому долгая, но продвигающаяся генерация не обрывается.
2. ~~**Недоступность потребителя вешает очередь.**~~ **Исправлено.** `send_json()` ждал
   подключения моста бесконечно, поэтому при неподнятом `chat-svc` первый же джоб вставал на
   `generation_started` и очередь замирала. Теперь ожидание ограничено
   `BRIDGE_SEND_TIMEOUT_SEC`, а состояние моста проверяется при запуске и видно в `/ping`.
   Отказ стартовать при недоступном `chat-svc` намеренно не делается: зависимость взаимная,
   и это создало бы цикл при подъёме стека.
3. ~~**Ошибка ретривала проглатывается.**~~ **Исправлено.** Раньше джоб продолжался с пустым
   контекстом, и пользователь получал ответ без источников, никак не помеченный как
   недостоверный. Теперь провал ретривала — ошибка всей генерации: по официальным вопросам
   ответ без опоры на документы хуже честной ошибки.
4. ~~**Размерность эмбеддингов рассогласована в трёх местах.**~~ **Исправлено.** `ingest-worker`
   объявлял `Vector(1536)` и дополнял/обрезал векторы, а колонки
   `library.chunk_embeddings.embedding` и `graph.entities.name_embedding` — `VECTOR(1024)`;
   вдобавок воркер грузил собственную модель вместо `embedding-svc`, то есть источников
   эмбеддингов было два. Теперь источник один, размерность объявлена один раз и проверяется
   при запуске. Разбор и процедура смены модели — [§13.1](#131-размерность-эмбеддингов-проблема-4).
   **На существующей базе** документы, упавшие до правки, остались в статусе `failed` и
   требуют переиндексации.

**Функциональные пробелы:**

5. ~~**Истории диалога нет в контракте.**~~ **Исправлено.** Добавлено поле `history` (§5.1):
   реплики идут и в промпт, и в извлечение сущностей — без второго уточняющие и местоименные
   вопросы («а что насчёт пересдачи по ней же?») не давали ни одной сущности.
6. ~~**`JUDGE_MODE=heuristic` объявлен, но не реализован.**~~ **Снято:** `judge` удалён вместе с
   прежним ретривалом.
7. ~~**Источники отдаются только как UUID.**~~ **Исправлено.** В `message_completed` добавлено
   поле `sources` с названиями документов; UUID сохранены (см. §5.2).
8. ~~**Векторный поиск не фильтрует по статусу документа.**~~ **Исправлено.** Добавлены фильтры
   по `ingest_status = 'indexed'` и по модели эмбеддингов (`embedding_model`).
9. ~~**Граф только растёт.**~~ **Частично исправлено.** Появились инструменты курирования
   (`/internal/graph/*` + раздел «Граф» в db-svc, §13.3): склейка дубликатов, смена типа,
   удаление со стоп-листом и отчёт по «сиротам» — сущностям без связей и без источников.
   Автоматической вычистки при переиндексации документов по-прежнему нет, чистка ручная.
10. ~~**Периодическая синхронизация истории сессии отключена.**~~ **Удалена.** Функция
    вырезана целиком вместе с эндпоинтом `/summarize_and_rules`, схемой `SummarizeRequest`,
    методом `_maybe_submit_periodic_history` и redis-гейтом в `chat-svc` (§13.2).
11. ~~**Нет отмены запроса.**~~ **Исправлено.** `POST /cancel` останавливает и активную, и
    стоящую в очереди генерацию; отмена кооперативная, накопленный текст сохраняется.
    Событие `message_cancelled`, команда `cancel` в WS-протоколе chat-svc и кнопка
    «Остановить» во фронтенде.
12. **Ничего не проверено на живом стеке** (см. §0; пайплайн ноутбука проверен сквозным тестом
    на одноразовых контейнерах, ниже — состояние graph-пути). Это не один из пунктов списка, а
    состояние всего остального: graph-builder не запускался ни разу, поэтому в `graph.*` нет
    ни одной строки, и весь graph-путь (извлечение → резолюция → обход → сборка контекста)
    никогда не исполнялся на реальных данных.

**Найдено при реализации (ещё не исправлено):**

13. **Пересборка графа непрозрачна и живёт в веб-процессе.** `stats_json` в
    `graph.extraction_runs` пишется только по завершении прогона, поэтому во время долгой
    пересборки статус — просто `running` без чисел, и понять, идёт ли работа, нельзя.
    Вдобавок `POST /internal/graph/build` запускает её `asyncio.create_task` внутри процесса
    API: многочасовой прогон конкурирует с обработкой запросов и пропадает при рестарте.
    Нужны инкрементальные обновления статистики и вынос в отдельный процесс/воркер.
14. **Стоимость первой сборки не оценена.** На каждое окно чанков делается отдельный вызов
    LLM, без батчинга и без возможности продолжить прерванный прогон. Сколько это займёт на
    реальном корпусе — неизвестно, потому что прогона не было.
15. **Почти все сущности будут `unknown`.** `classify_entity_type()` присваивает тип только
    при буквальном совпадении с фиксированным списком онтологии, всё остальное — `unknown`.
    При этом `_find_by_similarity()` ищет похожие сущности **внутри одного типа**, поэтому
    склейка дубликатов по эмбеддингу работает в основном внутри корзины `unknown`.
    Насколько это испортит граф, будет видно только после первой сборки.
16. **Обход графа не ранжирует.** Чанки сортируются только по числу переходов до сущности
    вопроса (`ORDER BY hop`), релевантности внутри одного расстояния нет. Вокруг «хабовых»
    сущностей вроде «Студент» два перехода могут покрыть почти весь граф, и в контекст
    попадут произвольные 8 чанков. Это главный риск качества graph-пути, и проверяется он
    только на живых данных.
17. **Карточка сущности не ограничивает связи.** `/internal/graph/entities/{id}` отдаёт все
    связи без пагинации — для хабовой сущности это тысячи строк в одном ответе.

**Вес образа:**

> Снято полностью: провайдеров LLM в сервисе больше нет (`llm_backends.py`, `requirements-local.txt`
> и build-аргумент `WITH_LOCAL_LLM` удалены, LLM — через `llm-proxy`). Текст ниже — история.

**13. `torch`/`transformers`/`accelerate` ставились всегда, хотя нужны только провайдеру
`local`. — Решено.** Оба места, где они импортируются (`app/ontology/llm_backend.py`,
`app/generation/llm_backends.py`), делают это лениво, внутри функций провайдера `local`,
помеченного как непригодный для прод-среды. При `LLM_PROVIDER=stub`/`ollama`/`openai` эти
пакеты не загружались ни разу, но в образ попадали всегда. Пина не было: `torch>=2.2.0`
разрешался в свежайшую сборку с CUDA 13, и pip тянул полный набор колёс `nvidia-*` — около
5 ГБ, порядка часа на обычном канале, с падением по таймауту DNS к `pypi.nvidia.com`.

Теперь они вынесены в `requirements-local.txt`, а Dockerfile ставит его содержимое только
при build-аргументе `WITH_LOCAL_LLM=true` (в compose пробрасывается из
`GRAPH_RAG_WITH_LOCAL_LLM`, по умолчанию `false`). Версия torch запинена той же, что в
`embedding-svc` — там он используется по-настоящему, и эта пара «версия + индекс» в проекте
уже проверена. Оба backend'а при отсутствии пакетов сообщают, что нужно пересобрать образ с
этим флагом или взять `ollama`, вместо голого `ImportError`.

Для сравнения: у `embedding-svc` torch остаётся в основном `requirements.txt` — там он
действительно работает, и объём образа оправдан.

## 10. Совместное использование двумя проектами

### 10.1 Контекст

Над сервисом работают две команды, и он для них общий:

| | Наш проект | Соседний проект |
| :-- | :-- | :-- |
| Интерфейс пользователя | Веб-чат (React) | Telegram-бот |
| Архитектура | Микросервисы + nginx | Монолит, без микросервисов |
| Оркестратор диалога | `chat-svc` | сам бот |
| Транспорт ответа | WebSocket, потоковая отдача | готовый текст одним сообщением |
| Хранение истории | `chat.messages` + Redis | своё |
| База данных | наша | **наша же** |
| Обновление документов | наш краулер (ещё не написан) | **наш же краулер** |

То есть общими являются: **этот сервис, база данных и краулер**. Различается всё, что
касается доставки ответа пользователю и хранения диалога.

| D12 | Очередь и нагрузка | одна общая очередь | одна общая очередь | нагрузка одной команды блокирует другую |
| D13 | Аутентификация | клиентский сертификат (mTLS) | та же схема | да, нужен только выданный сертификат |
| D14 | Запись в граф | `build_graph` пишет | должны только читать | не разграничено |

### 10.3 Три жёстких несовместимости — разбор

Различия D1–D3 не косметические, это блокеры: сегодня соседний проект физически не может
использовать сервис.

**D1. Ответ уходит не туда, откуда пришёл запрос.**
`POST /generate` возвращает `202` и кладёт джоб в очередь. Готовый ответ отправляется в
исходящее WebSocket-соединение, которое сервис открывает **сам** к `chat-svc`
(`app/generation/job_queue.py::ChatBridge`). Для бота это означает: (а) ответ приходит
в сервис, которого у них нет; (б) `send_json()` ждёт подключения моста без таймаута, поэтому
без `chat-svc` первый же джоб зависает навсегда и блокирует очередь; (в) зависание наступает
на `generation_started`, то есть ещё до всякой полезной работы.

**D2. В обязательных полях — первичные ключи нашей схемы `chat`.**
`request_id`, `session_id`, `user_id`, `message_id`, `assistant_message_id` обязательны все.
`assistant_message_id` — это UUID строки в `chat.messages`, по нему `chat-svc` находит
pending-запрос в Redis. У бота нет ни сессий, ни строк сообщений в нашей БД. Формально поля
типизированы как `str`, но семантически это чужие идентификаторы, и придумывать их «лишь бы
прошла валидация» — плохой контракт.

**D3. Ответ существует только как поток дельт.**
Полный текст нигде не передаётся: его склеивает потребитель. Боту нужен цельный текст, причём
не длиннее 4096 символов (лимит сообщения Telegram), а в системном промпте нет никаких
указаний на длину.

Остальные различия (D4–D14) решаются настройками и небольшими добавлениями в контракт —
при условии, что D1–D3 закрыты.

## 11. Компромисс по контракту — реализован

> **Статус: реализовано.** Ниже — исходное обоснование; фактический контракт описан в §5.1.
> Отличие от первоначального предложения одно: режим `stream` (SSE) не делался — соседняя
> команда подтвердила, что стриминг им не нужен (§12.3, вопрос 2).

### 11.1 Идея

Разделить **«что сервис вычисляет»** и **«куда он отдаёт результат»**. Пайплайн
(ретривал → сборка промпта → генерация) остаётся ровно один и общий; меняется только приёмник
результата. Это добавляет соседнему проекту нужный ему режим, ничего не ломая у нас.

Технически: в `app/generation/sinks.py` введён интерфейс приёмника с методами
(`started` / `chunk` / `completed` / `error` / `cancelled`) и реализации:

| Реализация | Режим | Кто использует |
| :-- | :-- | :-- |
| `ChatBridgeSink` | `ws_bridge` | наш `chat-svc` — текущее поведение, без изменений |
| `BufferSink` | `sync` | Telegram-бот — копит текст и возвращает его в HTTP-ответе |
| ~~`SseSink`~~ | ~~`stream`~~ | не реализован — стриминг без WebSocket никому не понадобился |

`process_job(job)` становится `process_job(job, sink)`; тела ретривала и генерации не меняются.
Объём работы — порядка сотни строк, риск для нашего пути минимальный, так как `ChatBridgeSink`
дословно повторяет текущий код.

### 11.2 Предлагаемый контракт `/generate`

Обязательным остаётся только `question`. Всё, что специфично для чата, уезжает в отдельный
объект `delivery`, который соседний проект просто не заполняет.

```jsonc
POST /generate
{
  "question": "Как получить справку об обучении?",   // единственное обязательное поле

  "response_mode": "sync",              // "sync" | "ws_bridge"  (по умолчанию "sync"; "stream" не реализован)

  "request_id": "...",                  // опц., генерируется сервисом, если не передан
  "user_id": "tg:123456",               // опц., произвольная строка, не обязана быть UUID
  "session_id": "tg:123456",            // опц., используется только для логов и аналитики
  "profile": { "year": 1 },             // опц.
  "history": [                          // опц., последние N реплик — закрывает пробел F11
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ],

  "delivery": {                         // обязателен ТОЛЬКО при response_mode = "ws_bridge"
    "assistant_message_id": "...",
    "message_id": "..."
  }
}
```

Поля `route` и `answer.max_chars` из проекта контракта убраны: `GenerateRequest` их не содержит,
и если клиент их передаст, они молча игнорируются.

Ответ в режиме `sync`:

```jsonc
200 OK
{
  "request_id": "...",
  "answer": "Справку об обучении можно получить ...",
  "route_used": "hybrid",                      // сейчас: quick_answer | hybrid (§5.1)
  "sources": [                                 // закрывает D5 / F13
    { "doc_id": "...", "title": "Положение об организации ...",
      "chunk_ids": ["...", "..."], "score": 0.82 }
  ],
  "retrieval": { "retrieval_ms": 431, "chunks_used": 6 },
  "usage": { "prompt_tokens": 1820, "completion_tokens": 240, "total_tokens": 2060 }
}
```

В режиме `stream` — тот же HTTP-запрос, ответ `text/event-stream` с теми же именами событий,
что у WS-моста, чтобы словарь событий в системе был один.
В режиме `ws_bridge` — всё как сейчас, слово в слово.

### 11.3 Что это даёт каждой стороне

**Соседнему проекту:** обычный синхронный HTTP-вызов — отправил вопрос, получил текст и
источники. Ни WebSocket, ни chat-svc, ни чужих UUID. При желании — `stream` для «печатает…».

**Нам:** ничего не ломается (`ws_bridge` остаётся дефолтом для `chat-svc`), но появляются
две вещи, которые нам самим нужны: поле `history` (пробел F11, который мы уже зафиксировали
как критичный для graph-RAG) и человекочитаемые `sources` (F13, они нужны, чтобы показывать
студенту, на каком документе основан ответ).

**Обоим:** `route` и `max_chars` на уровне запроса снимают D9 и D4 без раздвоения конфигурации,
а сам факт наличия второго потребителя заставляет закрыть проблемы устойчивости §9.1–9.3,
которые и так надо чинить.

### 11.4 Сопутствующие изменения, без которых компромисс неполон

| Что | Зачем | Связь |
| :-- | :-- | :-- |
| Таймаут на все вызовы LLM | иначе один зависший провайдер вешает обе команды | §9.1 |
| Таймаут на ожидание WS-моста | иначе недоступность `chat-svc` вешает и запросы бота | §9.2, D1 |
| `title` документа в `RetrievedChunk` (join `library.documents`) | без него `sources` не собрать | D5 |
| Согласованная политика при провале ретривала | ответ без источников по официальному вопросу опасен | §9.3 |
| Указание длины ответа в системном промпте | лимит Telegram 4096 | D4 |
| Раздельные очереди либо раздельные экземпляры | нагрузка одной команды не должна блокировать другую | D12 |

### 11.5 Чего делать НЕ стоит

- **Не делать второй сервис-обёртку для бота.** Это ровно та ошибка, из-за которой мы
  объединяли `rag-svc` и `llm-svc`: лишний сетевой хоп и вторая копия логики.
- **Не форкать репозиторий.** Разойдутся онтология и промпты, а граф в общей БД один —
  результат будет непредсказуем для обеих команд.
- **Не заставлять бота имитировать `chat-svc`** (поднимать WS-эндпоинт и придумывать UUID).
  Это переносит нашу архитектурную специфику в чужой проект.
- **Не разносить извлечение сущностей на две реализации** — прямое нарушение решения №5 (§3).

## 12. Модель владения и открытые вопросы

### 12.1 Предлагаемая модель развёртывания

**Общий образ и общая БД, но отдельные экземпляры сервиса у каждой команды.**

Причины: у команд разная конфигурация (провайдер LLM, режим ретривала, персона), разный
профиль нагрузки и разный цикл релизов. Общий — код и данные, а не процесс. Это же снимает D12.

| Что | Владелец | Правило |
| :-- | :-- | :-- |
| Репозиторий сервиса, онтология, промпты | общее | изменения — через совместное ревью |
| **Граф: наполнение и курирование** | **соседняя команда** | они запускают пересборку и правят содержимое графа |
| Схема `graph` (DDL, миграции) | общее | меняется вместе с онтологией, через совместное ревью |
| Схема `library`, `ingest-worker`, краулер | наша команда | соседи — потребители |
| Схема `chat` | наша команда | соседей не касается |
| Экземпляр сервиса и его `.env` | каждая команда свой | конфигурация не общая |
| Хранение диалогов, UI, доставка пользователю | каждая команда своя | сервиса не касается |

> **Изменение относительно первой редакции.** Раньше здесь предполагалось, что граф
> наполняем мы, а экземпляр соседней команды работает с ним только на чтение. Решено
> наоборот: **граф целиком переходит к соседней команде** — и построение, и курирование.
> Мы отвечаем за поставку данных, из которых он строится (краулер → `library.documents` →
> `ingest-worker` → `library.chunks`), и остаёмся потребителями готового графа.

**Про разграничение прав в БД.** Изначально предполагалось сделать его не договорённостью,
а правами: соседняя команда пишет в `graph` как `graph_user`, наш экземпляр получает роль
только на чтение. **От этого пришлось отказаться**: UI курирования графа живёт в нашем `db-svc`
и ходит через наш же экземпляр `graph-rag-svc` — с read-only ролью курирование сломалось бы.

Поэтому оба экземпляра подключаются как `graph_user` и оба могут писать в `graph` и в `rag`,
а «кто наполняет граф» остаётся процессной договорённостью. Технически принудительным остаётся
только запуск пересборки: `GRAPH_BUILD_API_ENABLED=false` в прод-конфигурации закрывает кнопку
пересборки через API (CLI при этом продолжает работать).

Если разграничение всё-таки нужно принудительным — тогда UI курирования должен ходить в
экземпляр соседней команды, а не в наш; это надо решать вместе с ними.

### 12.2 Правило изменения онтологии

Онтология (`app/ontology/schema.py`, `prompts.py`) — общий контракт: она определяет, какие
узлы попадают в граф, а граф в БД один на обе команды. Поэтому любое изменение требует:
совместного ревью → повышения `ONTOLOGY_VERSION` → полной пересборки графа. После пересборки
ответы меняются **у обеих команд одновременно** — это нужно планировать, а не обнаруживать.

по §12.1 наш экземпляр будет иметь там только чтение. Нужна отдельная схема (например, `rag`)
с правом записи у обоих экземпляров.

Решено **оставить обе таблицы**: `chat.rag_runs` продолжает писать `chat-svc` (там есть связь
с `message_id`, которой у бота нет), а нейтральную таблицу пишет сам сервис — для аналитики,
общей по обоим проектам. Дублирование осознанное; схлопнуть можно позже.

**Вынос загрузки модели (вопрос 7).** Отдельный контейнер для генерации у нас уже есть — это
`ollama`; провайдеры `openai` и `ollama` ничего не грузят в процесс. Загружает модель
в процесс только backend `local` (`transformers` + `torch`). Предлагается его убрать: тогда
из `graph-rag-svc` уходят `torch`/`transformers`/`accelerate`, образ становится значительно
легче, а пересборка сервиса перестаёт затрагивать модель — ровно то, ради чего вопрос и
задавался. Если понадобится конкретная HF-модель, которой нет в ollama, под неё заводится
отдельный сервис по образцу `embedding-svc`, а не in-process загрузка.

## 13. Проектные решения по открытым проблемам

### 13.1 Размерность эмбеддингов (проблема 4)

> **Октябрь 2026: модель сменена на `intfloat/multilingual-e5-base` (768).** Колонки
> `library.chunk_embeddings.embedding`, `library.quick_answer_variants.embedding`,
> `library.links.embedding` — `VECTOR(768)` (миграция `011_notebook_pipeline.sql` очищает старые
> векторы и возвращает документы в `pending`); `graph.entities.name_embedding` осталась
> `VECTOR(1024)` и не проверяется (граф отключён). Порядок перехода на существующем стенде —
> `main/deploy.md`, «Миграция на e5». Таблицы ниже описывают состояние до перехода (bge-m3, 1024).

#### Что происходит сейчас

| Место | Что объявлено | Кто пишет |
| :-- | :-- | :-- |
| `library.chunk_embeddings.embedding` | `VECTOR(1024)` | `ingest-worker` |
| `graph.entities.name_embedding` | `VECTOR(1024)` | `graph-rag-svc` |
| `ingest-worker/app/main.py:176` | `Vector(1536)` | — |
| `embedding-svc` (`BAAI/bge-m3`) | 1024 измерения | — |

`ingest-worker._embed()` дополняет короткие векторы нулями до 1536 **и обрезает** длинные
(`v_list[:1536]`), после чего пытается вставить их в колонку `VECTOR(1024)`. pgvector такую
вставку отклоняет, а поскольку чанки и эмбеддинги пишутся одной транзакцией, откатываются и
чанки: документ целиком получает `ingest_status='failed'`.

Обнаружились ещё две вещи, которых не было видно раньше:

- **В системе два независимых источника эмбеддингов.** `ingest-worker` не ходит в
  `embedding-svc`, а грузит собственный `SentenceTransformer` (`app/main.py:190`). Совпадение
  моделей держится только на том, что в обоих `.env` одинаковое значение
  `EMBEDDER_MODEL_NAME`. Разъедутся значения — чанки и запросы окажутся в разных векторных
  пространствах, и поиск начнёт молча выдавать мусор, без единой ошибки.
- **При неудачной загрузке модели `_embed()` возвращает векторы из одних нулей.** У нулевого
  вектора нулевая норма, а косинусное расстояние в этом случае не определено — такие строки
  отравляют выдачу поиска, не вызывая ошибок.

#### Про идею «объявить размерность с запасом и дополнять нулями»

**Математически идея верна.** Если дополнить нулями и хранимые векторы, и вектор запроса, то
скалярное произведение не меняется (нули ничего не добавляют), нормы не меняются — значит,
косинусная близость, L2 и inner product сохраняются **точно**. Ранжирование не поедет.

**Но проблему она не решает,** и вот почему:

1. **Сравнимость векторов определяется моделью, а не размерностью.** Если сменить модель,
   старые и новые векторы будут из разных пространств. Дополнение нулями позволит хранить их
   в одной колонке — то есть превратит явную ошибку вставки в молчаливо неверную выдачу
   поиска. Сейчас несовпадение хотя бы падает громко.
2. **Обрезка длинных векторов разрушительна.** В текущем коде есть не только дополнение, но и
   `v_list[:1536]`. Если модель когда-нибудь вернёт больше — вектор просто испортится.
3. **Есть потолок.** Тип `vector` в pgvector допускает до 16000 измерений, но индексы
   `hnsw`/`ivfflat` — только до 2000. Запас «на будущее» упрётся в это ограничение.
4. **Цена.** Каждое измерение — 4 байта. Запас 1024 → 1536 это 2 КБ мусора на вектор
   (≈200 МБ на 100 тыс. чанков) плюс замедление построения и обхода индекса, который считает
   расстояния по всем измерениям, включая нулевые.

Итог: запас нулями — это способ **отложить** проблему смены модели, заплатив местом и
скоростью и потеряв единственную защиту (громкую ошибку). Смену модели он не переживает всё
равно — переиндексация всё равно понадобится.

#### Что решать на самом деле

Настоящее требование звучит не «пусть влезает вектор любого размера», а: **система должна
переживать смену модели эмбеддингов, не выдавая при этом молча неверных результатов.** Для
этого нужны три вещи: одна модель на всю систему, проверка согласованности при запуске и
явная процедура переиндексации.

#### Варианты

**Вариант A — рекомендуемый: единый embedder + проверка при запуске + процедура переиндексации.**

1. **Один источник эмбеддингов.** `ingest-worker` перестаёт грузить свой
   `SentenceTransformer` и вызывает `embedding-svc /embed`, как это уже делает
   `graph-rag-svc`. Модель определяется в одном месте, worker становится легче (уходит
   зависимость от `torch`), а путь «модель не загрузилась → нулевые векторы» исчезает сам:
   неудачный HTTP-вызов честно роняет обработку документа.
2. **Размерность объявляется один раз.** `EMBEDDING_DIM` в корневом `main/.env`, оттуда — в
   `init.sql` через `\set` (обе колонки), в миграции и в конфиги сервисов.
3. **Проверка при запуске.** `ingest-worker` и `graph-rag-svc` на старте спрашивают у
   `embedding-svc` `GET /ping` (он уже отдаёт `dimension`) и сравнивают с фактической
   размерностью колонки в БД:
   ```sql
   SELECT atttypmod FROM pg_attribute
   WHERE attrelid = 'library.chunk_embeddings'::regclass AND attname = 'embedding';
   ```
   Не совпало — сервис не стартует и пишет в лог, что именно с чем разошлось. Это тот же
   принцип «проверять заранее, а не падать в рантайме», что и в решении по проблеме 2.
4. **Никаких дополнений и обрезок.** Длина вектора не совпала — это ошибка, а не повод
   подгонять данные.
5. **Чтение фильтруется по модели.** В `library.chunk_embeddings` и `graph.entities` уже есть
   колонка `embedding_model`; векторный поиск добавляет `WHERE embedding_model = :active_model`.
   Это же требуется по проблеме 8.
6. **Смена модели — задокументированная процедура, а не сюрприз.** Новая колонка нужной
   размерности → фоновая переэмбеддинг-задача заполняет её → переключение активной модели →
   старая колонка удаляется. Благодаря фильтру из п. 5 незавершённая миграция даёт
   *меньше* результатов, но никогда — неверные.

**Вариант B — минимальный хотфикс:** в `ingest-worker` заменить `Vector(1536)` на
`Vector(1024)` и убрать дополнение/обрезку. Две строки, ингест начинает работать сегодня.
Хрупкость (два embedder'а, отсутствие проверок) остаётся.

**Вариант C — как предлагалось, с запасом:** объявить везде `VECTOR(1536)` и дополнять нулями.
Работает, но по причинам выше не рекомендуется.

#### Принято и реализовано: вариант A

Решение владельца проекта: делать сразу A, минуя промежуточный хотфикс. Эмбеддинги считает
только `embedding-svc`; смена модели эмбеддингов означает пересчёт всех чанков и полную
пересборку графа — это принятая цена, а не то, чего пытаются избежать.

Что сделано:

| Где | Изменение |
| :-- | :-- |
| `ingest-worker/app/main.py` | Убран собственный `SentenceTransformer`; `_embed()` вызывает `embedding-svc /embed`; дополнение нулями и обрезка удалены; имя модели берётся из ответа сервиса, а не из локального `.env`; добавлена `verify_embedding_setup()` |
| `ingest-worker/requirements.txt` | Убран `sentence-transformers` |
| `graph-rag-svc/app/core/startup_checks.py` | Новый модуль: сверяет размерность модели в `embedding-svc` с `EMBEDDING_DIM` и с фактическим типом колонок `library.chunk_embeddings.embedding` и `graph.entities.name_embedding` |
| `graph-rag-svc/app/main.py` | Проверка выполняется на `startup` до запуска очереди — сервис не поднимается при расхождении |
| `graph-rag-svc/app/db/models.py` | `EMBEDDING_DIM` берётся из настроек; добавлена колонка `embedding_model` |
| `graph-rag-svc/app/retrieval/vector_retriever.py` | Поиск фильтруется по `embedding_model` (и по `ingest_status`, проблема 8) |
| `main/.env(.example)` | Добавлен `EMBEDDING_DIM=1024` — единый источник значения |
| `main/infra/db/init/init.sql`, `migrations/002_graph_schema.sql` | `VECTOR(1024)` → `VECTOR(:embedding_dim)` |
| `main/docker-compose.yml` | `ingest-worker` получил `EMBEDDING_SVC_URL`/`EMBEDDING_DIM` и `depends_on: embedding-svc` |

Проверка при запуске выполняется с повторами (модель в `embedding-svc` грузится не мгновенно),
а при реальном расхождении сервис останавливается с сообщением, что именно с чем разошлось.

#### Процедура смены модели эмбеддингов

1. Поднять новую модель в `embedding-svc`, узнать её размерность (`GET /ping`).
2. Обновить `EMBEDDING_DIM` в `main/.env` и тип колонок в БД.
3. Пересчитать эмбеддинги всех чанков: сбросить документы в `ingest_status='pending'`,
   дать `ingest-worker` переиндексировать их.
4. Полностью пересобрать граф: `python -m cli.build_graph --full-rebuild` (эмбеддинги имён
   сущностей считаются той же моделью и тоже устаревают).
5. Удалить строки, оставшиеся от старой модели — они отличаются по `embedding_model`.

Пока переиндексация не завершена, поиск фильтрует по имени модели и поэтому выдаёт меньше
результатов, но никогда — вычисленные в чужом векторном пространстве.

> Замечание про уже накопленные данные: если в БД остались строки, записанные разными
> моделями или нулевыми векторами (их создавал прежний `_embed()` при неудачной загрузке
> модели), их нужно удалить и переиндексировать. Нулевые векторы находятся условием
> `embedding <-> embedding = 0`.

### 13.2 Периодическая сводка сессии — удаляется (проблема 10)

> **Выполнено: функция вырезана полностью.** Редизайн ниже был предложен и разобран, но
> владелец проекта счёл саму функцию ненужной. Удалены: `_maybe_submit_periodic_history`
> и её точка вызова в `chat-svc`, redis-гейт `periodic_rag_gate`, эндпоинт
> `/summarize_and_rules` и схема `SummarizeRequest` в этом сервисе (он существовал именно
> под эту функцию и больше никем не вызывался). Разбор ниже сохранён как обоснование.

#### Что это было

`chat-svc._maybe_submit_periodic_history` собирал последние сообщения сессии и прошлые
`rag_runs`, заводил pending-запрос (тот же механизм, что для обычного ответа) и слал это в
`rag-svc` с типом `"periodic_session_history"`, ожидая потоковый ответ через тот же WS-мост.
Обработчика для этого типа не было ни на одной стороне.

#### Почему прежняя схема была неправильной

Она переиспользовала путь потоковой генерации ответа для того, что ответом не является.
Отсюда всё остальное: фиктивное assistant-сообщение, pending-запрос, ожидание стрима и
контракт, который не совпадал ни с чем.

**Кроме того, половина исходной мотивации отпала.** Периодическая синхронизация нужна была,
чтобы модель хоть как-то видела контекст сессии. С решением по проблеме 5 история диалога
приходит в `/generate` при каждом вопросе — отдельный механизм для этого больше не нужен.

Остаётся вторая, самостоятельная функция: **сводка прогресса студента и правила/рекомендации**.
Это уже не про контекст ответа, а отдельный продуктовый артефакт.

#### Предлагаемый редизайн

1. **Убрать механику стриминга целиком.** Никакого pending-запроса, никакого фиктивного
   assistant-сообщения, никакого WS-моста.
2. **Сделать это обычным синхронным вызовом.** Эндпоинт `/summarize_and_rules` уже существует,
   уже синхронный, возвращает `{summary, rules}` прямо в HTTP-ответе — и сейчас его никто не
   вызывает. Это ровно то, что нужно.
3. **Перенести ретривал внутрь эндпоинта.** Сейчас он требует, чтобы чанки передала вызывающая
   сторона, — а у `chat-svc` их нет. Добавить флаг `retrieve: true`, при котором сервис сам
   собирает контекст через тот же `orchestrator.retrieve()` по темам сессии.
4. **Изменить триггер.** Не «раз в N дней при следующем вопросе», а явно: по кнопке
   пользователя («подведи итоги»), либо фоновой задачей при завершении/простое сессии.
   Скрытый триггер внутри обработки вопроса и был причиной того, что фича ломала основной путь.
5. **Хранить результат отдельно** — новая таблица `chat.session_summaries`
   (`session_id`, `summary`, `rules_json`, `based_on_message_id`, `created_at`), а не в виде
   сообщения в переписке.

Итоговый контракт:

```jsonc
POST /summarize_and_rules
{ "messages": [{"role":"user","content":"..."}], "retrieve": true }
→ 200 { "summary": "...", "rules": ["..."], "sources": [{"doc_id":"...","title":"..."}] }
```

> Более дешёвая альтернатива, если фича не нужна как продукт: удалить точку вызова в
> `chat-svc` и эндпоинт целиком. Сейчас код существует, но не работает ни в каком виде, и это
> худшее из состояний.

### 13.3 Внутреннее API курирования графа (проблема 9) — реализовано

#### Где это должно жить и почему

Первоначально предполагалось сделать редактирование графа в `db-svc` — он уже умеет
CRUD по любым таблицам любой схемы. **Решено делать иначе: отдельным внутренним API внутри
этого сервиса.**

Причины:

1. **Граф целиком переходит к соседней команде** — и его построение, и курирование (см.
   обновлённую модель владения в §12.1). А в `db-svc` эта команда не ориентируется: это наш
   внутренний инструмент контент-менеджера со своим фронтендом и своими соглашениями.
2. **Все механизмы работы с графом должны лежать в одном месте.** Резолюция сущностей,
   алиасинг, upsert-правила и обход уже реализованы здесь (`app/graph/`). Если положить
   редактирование в `db-svc`, эти правила придётся продублировать на голом SQL — и они
   разъедутся с билдером при первом же изменении.
3. Общий CRUD по таблицам для графа всё равно непригоден: править граф построчно — значит
   работать с голыми UUID, не видя, что с чем связано и из какого текста это извлечено.

Реальные задачи курирования:

- **Склеить дубликаты сущностей** — «Учебный офис», «учебный офис», «УО» становятся тремя
  разными узлами. Это главная и самая частая операция.
- **Исправить `entity_type`** у сущностей, которым автоклассификатор поставил `"unknown"`.
- **Удалить мусор** от неудачных извлечений.
- **Посмотреть сущность целиком**: алиасы, связи в обе стороны, чанки-источники **с текстом**
  и названием документа — иначе нельзя понять, корректно ли извлечение.
- **Вычистить устаревшее** после удаления документов (та самая проблема «граф только растёт»).

#### Ключевое ограничение: правки должны переживать пересборку графа

Без этого инструмент бесполезен: `build_graph` работает через upsert по естественным ключам,
поэтому следующая же пересборка заново создаст сущность, которую вручную склеили или удалили.

| Операция | Как сделать устойчивой к пересборке |
| :-- | :-- | 
| **Склейка (merge)** | Перенести связи и провенанс на целевую сущность, а имя удаляемой **записать её алиасом**. Дальше `resolve_entity()` при следующем извлечении найдёт строку по алиасу и вернёт целевую сущность. Операция самозалечивающаяся — работает *вместе* с билдером, а не против него. |
| **Правка `entity_type`** | Пометить сущность как курированную (`attributes_json.curated = true`); билдер не перезаписывает курированные поля. |
| **Удаление мусора** | Одного удаления мало — извлечение создаст запись снова. Нужен стоп-лист (`graph.curation_blocklist`), который проверяет `resolve_entity()`. |

Это требует небольших доработок и в `graph-rag-svc` (`resolution.py`, `store.py`), не только
в `db-svc`.

#### API

Группа `/internal/graph/*` в этом сервисе, за той же межсервисной аутентификацией, что и
остальные эндпоинты (§5.5). Реализуется поверх существующих модулей `app/graph/*`, а не
отдельным слоем SQL:

| Метод | Путь | Назначение |
| :-- | :-- | :-- |
| GET | `/internal/graph/stats` | счётчики: сущностей по типам, сколько `unknown`, связей, последние прогоны сборки |
| GET | `/internal/graph/entities?q=&type=&limit=` | поиск по каноническому имени и алиасам |
| GET | `/internal/graph/entities/{id}` | карточка: алиасы, связи в обе стороны с именами соседей, чанки-источники с текстом и названием документа |
| PATCH | `/internal/graph/entities/{id}` | правка `canonical_name` / `entity_type` / `attributes_json` (ставит `curated`) |
| POST | `/internal/graph/entities/{id}/merge` | склейка в `{target_id}` по правилам выше |
| POST/DELETE | `/internal/graph/entities/{id}/aliases[/{alias_id}]` | ручное управление алиасами |
| DELETE | `/internal/graph/entities/{id}` | удаление (каскадом) + опционально в стоп-лист |
| GET/PATCH/DELETE | `/internal/graph/relations` | работа со связями |
| GET | `/internal/graph/orphans` | сущности без связей и сущности, чьи документы-источники исчезли |
| POST | `/internal/graph/build` | запуск пересборки — то же, что `cli/build_graph.py`, но по HTTP |

При склейке нужно аккуратно обработать ограничения уникальности: если перенос связи создаёт
дубликат `(subject, object, relation)`, связь нужно удалить, а не обновлять. То же для алиасов
по `(entity_id, alias_normalized)`. Это ровно та логика, которую не следует дублировать вне
`app/graph/` — и главная причина, по которой API живёт здесь, а не в `db-svc`.

#### Интерфейс: раздел «Граф» в `db-svc` поверх этого API

Курировать граф удобно глазами, поэтому нужен UI: список сущностей с поиском, карточка
сущности с соседями и чанками-источниками, склейка выбором двух записей. Визуализация
подграфа полезна, но не обязательна — обязательны именно **склейка и смена типа**.

**Реализовано: UI сделан разделом в `db-svc`** — это админка проекта, и место для инструмента
контент-менеджера именно там. Файлы: `app/routes/graph.py` и `app/services/graph_rag.py`
(сквозной прокси), `app/static/js/api/graph.js`, `app/static/js/views/graph/`. Принципиальное ограничение: этот раздел ходит в
`/internal/graph/*`, а **не** в таблицы `graph.*` напрямую — иначе правила резолюции и
устойчивости к пересборке продублируются на голом SQL и разъедутся с билдером.

Следствие: `db-svc` впервые становится клиентом внутреннего API. Ему понадобятся
собственный сертификат (политика в `main/infra/mtls/graph-rag-svc.conf`) и сетевая доступность
`graph-rag-svc`. Запросы проксирует бэкенд `db-svc`, а не браузер.

**Права доступа к БД.** При переходе владения графом к соседней команде писать в схему `graph`
должен их экземпляр сервиса, а не наш — см. обновлённую §12.1.

## Подключение к PostgreSQL по сертификату

Если заданы `POSTGRES_SSLCERT`, `POSTGRES_SSLKEY` и `POSTGRES_SSLROOTCERT`, сервис входит в БД
по клиентскому сертификату (CN равен имени роли) вместо пароля и проверяет сервер: цепочку до
корня и имя хоста. Это делает `app/pg_tls.py`: он создаёт движок со своим `async_creator` и
собирает контекст TLS заново для каждого нового соединения, чтобы обновлённый сертификат
(он живёт сутки) подхватывался без перезапуска. Без этих переменных сервис работает как раньше,
по паролю из URL. Модуль одинаков во всех сервисах и лежит в каждом репозитории отдельной
копией, менять его нужно во всех сразу. Включение и проверка — `main/infra/db/README.md`.

## Вызовы других сервисов по mTLS

Так graph-rag-svc вызывает embedding-svc (`/embed`, стартовая проверка `/ping`), `llm-proxy` (`LLM_BASE_URL=https://llm-proxy:8443/v1`, прокси сам проверяет сертификат и пускает только CN `graph-rag-svc`) и подключается к chat-svc по внутреннему WebSocket (`CHAT_WS_URL=wss://chat-svc:8443/ws/internal/llm`; контекст TLS собирается заново при каждом подключении). Сам graph-rag-svc при включённом mTLS слушает только `127.0.0.1`, а наружу смотрит прокси на порту 8443, пропускающий chat-svc (`/generate`, `/cancel`) и db-svc (`/internal/graph/*` — сейчас маршрутов нет, GraphRAG отключён).

Если заданы `SERVICE_MTLS_CERT`, `SERVICE_MTLS_KEY` и `SERVICE_MTLS_CA`, сервис предъявляет свой
сертификат внутреннего CA (CN равен имени сервиса) и проверяет сервер. Контекст TLS собирается в
`app/mtls.py` заново при создании каждого HTTP-клиента, поэтому суточный сертификат,
обновлённый рядом лежащим контейнером, подхватывается без перезапуска. Без этих переменных
сервис ходит по открытому HTTP, а получатель должен быть в режиме `INTERNAL_AUTH_MODE=insecure`
(только для отладки). Получатели
(graph-rag-svc, embedding-svc) принимают вызовы только через прокси с проверкой сертификата и
политикой «кто что может» (`main/infra/mtls`). Модуль одинаков в chat-svc, db-svc,
graph-rag-svc и ingest-worker, менять его нужно во всех сразу. Включение и проверка —
`main/infra/pki/README.md`, раздел «mTLS между сервисами».

## Метрики

`GET /metrics` отдаёт Prometheus (за mTLS - только пользователю `prometheus`, политика в `infra/mtls/graph-rag-svc.conf`). Кроме HTTP-метрик (`http_requests_total`, `http_request_duration_seconds`, `http_requests_inprogress`; метка `handler` - шаблон маршрута) сервис отдаёт бизнес-метрики с префиксом `pochemuchnik_`. Код: `app/metrics.py`, тесты: `tests/`. Общая картина и дашборды - `infra/observability/README.md` в корневом репозитории.

| Метрика | Что считает |
| :-- | :-- |
| `generate_requests_total{mode}` | принятые запросы `/generate` (`sync`, `ws_bridge`) |
| `judge_decisions_total{route}` | маршрут ответа: `quick_answer` (готовый ответ без LLM), `hybrid` (поиск, реранк, ответ LLM). Судьи больше нет, имя метрики прежнее ради дашбордов; прежних меток `graph`, `vector`, `graph_to_vector` больше нет |
| `stage_duration_seconds{stage}` | `retrieval`, `generation`. `retrieval` теперь включает вызовы LLM на переписывание вопроса и реранк — на дашборде это скачок латентности поиска, а не деградация |
| `context_chunks` | число чанков в контексте (быстрые ответы не учитываются) |
| `empty_context_total` | запросы, для которых не нашлось ни одного чанка |
| `llm_errors_total` | ошибки генерации от провайдера LLM |
| `retrieval_failures_total` | сбои поиска контекста |
